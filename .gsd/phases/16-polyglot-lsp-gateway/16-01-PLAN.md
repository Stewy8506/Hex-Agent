# Plan 16.01: Polyglot LSP Client Core & Stdio Transport

<objective>
Implement a lightweight, zero-dependency Polyglot Language Server Protocol (LSP) client engine featuring JSON-RPC 2.0 Content-Length stdio framing, multi-language server registry with automatic executable discovery (Python, TypeScript/JavaScript, Go, Rust, C/C++, Java), core document synchronization (`didOpen`, `didChange`, `didClose`), and real-time diagnostic publication tracking (`textDocument/publishDiagnostics`).

Purpose: Provides HEX with real compiler awareness and language intelligence, laying the foundation for instant syntax/type error interception and IDE-grade code navigation tools.
Output: `src/harness_core/lsp/` module with client, transport, registry, and manager implementations, backed by complete unit tests in `tests/test_lsp_client.py`.
</objective>

<task type="auto">
  <name>Implement JSON-RPC 2.0 Base Protocol & Stdio Transport with Content-Length Framing</name>
  <files>src/harness_core/lsp/__init__.py, src/harness_core/lsp/client.py</files>
  <action>
    Create package directory `src/harness_core/lsp/` and initialize `src/harness_core/lsp/__init__.py`.
    In `src/harness_core/lsp/client.py`:
    1. Define core LSP data models:
       - `LSPMessage`: represents a JSON-RPC 2.0 request, response, or notification (`jsonrpc="2.0"`, `id`, `method`, `params`, `result`, `error`).
       - `LSPResponseError(Exception)`: raised on server-returned JSON-RPC error payloads with `code`, `message`, and `data`.
       - `LSPTimeoutError(TimeoutError)`: raised when a request exceeds timeout waiting for server response.
    2. Implement `StdioLSPTransport`:
       - Spawns language server subprocess via `subprocess.Popen` with `stdin=PIPE`, `stdout=PIPE`, `stderr=PIPE`, `bufsize=0`.
       - Outbound framing: formats payload as UTF-8 JSON, prepends `Content-Length: {len}\r\n\r\n`, and writes to `stdin.write()`, followed by `stdin.flush()`.
       - Inbound framing: background reader thread continuously reading `stdout` byte-stream. Parses HTTP-style headers until blank line (`\r\n` or `\n`), extracts `Content-Length`, reads exact body byte count, decodes UTF-8, and parses JSON.
       - Message demultiplexing:
         - Responses with `id` match against thread-safe pending request registry (`_pending: dict[int | str, tuple[threading.Event, dict[str, Any]]]`) and unblock waiting threads.
         - Server notifications (no `id`) dispatch to registered notification handlers (e.g. `textDocument/publishDiagnostics`, `window/logMessage`).
         - Server requests to client respond with empty or default result to prevent server hangs.
       - Asynchronous stderr logger thread collecting language server stderr lines into a rolling diagnostic deque (last 100 lines) for debugging.
       - Thread-safe `send_request(method, params, timeout=30.0) -> Any` returning the `result` field.
       - `send_notification(method, params) -> None` sending fire-and-forget notifications.
       - Clean `close()` terminating child process gracefully with timeout and SIGKILL fallback.

    AVOID: Using raw newline-delimited JSON-RPC without Content-Length headers, because standard language servers (pyright, rust-analyzer, clangd, gopls) strictly reject messages lacking HTTP-style `Content-Length: <n>\r\n\r\n` framing.
  </action>
  <verify>python -c "from harness_core.lsp.client import StdioLSPTransport, LSPMessage, LSPResponseError; print('LSP transport module imported successfully')"</verify>
  <done>Stdio transport correctly formats outbound messages with Content-Length headers, parses inbound framed payloads, demultiplexes request IDs, and dispatches server notifications.</done>
</task>

<task type="auto">
  <name>Implement Language Server Registry & Multi-Language Auto-Detection</name>
  <files>src/harness_core/lsp/registry.py</files>
  <action>
    In `src/harness_core/lsp/registry.py`:
    1. Define `LanguageServerSpec`:
       - `language_id`: canonical identifier (e.g., "python", "typescript", "javascript", "go", "rust", "cpp", "c", "java").
       - `server_name`: canonical server name (e.g., "pyright", "pylsp", "ruff", "typescript-language-server", "vtsls", "gopls", "rust-analyzer", "clangd", "jdtls").
       - `binary_candidates`: list of executable names to search in PATH via `shutil.which` (e.g., `["pyright-langserver", "pyright"]`, `["typescript-language-server"]`).
       - `default_args`: CLI flags required for stdio mode (e.g., `["--stdio"]` for pyright and typescript-language-server).
       - `file_extensions`: tuple of supported file extensions (e.g., `(".py", ".pyi")`, `(".ts", ".tsx", ".js", ".jsx")`, `(".go",)`, `(".rs",)`, `(".c", ".cpp", ".cc", ".cxx", ".h", ".hpp")`, `(".java",)`).
       - `root_markers`: list of marker files indicating workspace root (e.g., `["pyproject.toml", "setup.py", "requirements.txt"]`, `["package.json", "tsconfig.json"]`, `["go.mod"]`, `["Cargo.toml"]`, `["CMakeLists.txt", "compile_commands.json"]`, `["pom.xml", "build.gradle"]`).
       - `initialization_options`: dict of default initialization options.
    2. Implement `LanguageServerRegistry`:
       - Pre-register configurations for all 6 language families:
         1. Python: `pyright` (args: `["--stdio"]`), `pylsp` (args: `[]`), `ruff` (args: `["server"]`).
         2. TypeScript / JavaScript: `typescript-language-server` (args: `["--stdio"]`), `vtsls` (args: `["--stdio"]`).
         3. Go: `gopls` (args: `[]`).
         4. Rust: `rust-analyzer` (args: `[]`).
         5. C / C++: `clangd` (args: `[]`).
         6. Java: `jdtls` (args: `[]`).
       - `find_server_for_file(file_path: Path | str, workspace_root: Path | str | None = None) -> LanguageServerSpec | None`:
         Matches file extension, checks root markers, and verifies executable presence with `shutil.which`. If multiple candidates match, chooses the first available on `PATH`.
       - `detect_workspace_servers(workspace_root: Path | str) -> list[LanguageServerSpec]`:
         Discovers all language servers applicable to the repository layout, cross-referencing with `detect_recipe` from `src/harness_core/recipes.py` when available.
       - Allow custom server specification registration via `register_server(spec, priority=0)`.

    AVOID: Hardcoding absolute paths to binaries; use `shutil.which` and allow environment variable overrides (e.g., `HEX_LSP_PYTHON_BIN`, `HEX_LSP_TS_BIN`).
  </action>
  <verify>python -c "from harness_core.lsp.registry import LanguageServerRegistry; reg = LanguageServerRegistry(); print('Registered language servers:', len(reg.get_all_specs()))"</verify>
  <done>Registry defines specifications for Python, TS/JS, Go, Rust, C/C++, and Java, and correctly resolves candidate servers based on file extension and project root markers.</done>
</task>

<task type="auto">
  <name>Implement LSP Client Lifecycle, Document Synchronization, Diagnostic Store & Unit Tests</name>
  <files>src/harness_core/lsp/client.py, src/harness_core/lsp/manager.py, tests/test_lsp_client.py</files>
  <action>
    In `src/harness_core/lsp/client.py`:
    1. Implement `LSPClient`:
       - Lifecycle methods:
         - `initialize(workspace_root: Path | str) -> dict`: sends `initialize` request with client capabilities (`textDocument.publishDiagnostics`, `hover`, `definition`, `references`), sets `rootUri` and `rootPath`, awaits response, and sends `initialized` notification.
         - `shutdown() -> None`: sends `shutdown` request followed by `exit` notification, then closes transport.
       - Document synchronization:
         - `did_open(file_path: Path | str, text: str | None = None, language_id: str | None = None) -> None`: sends `textDocument/didOpen` with `TextDocumentItem`.
         - `did_change(file_path: Path | str, text: str, version: int = 1) -> None`: sends `textDocument/didChange` with full document content.
         - `did_close(file_path: Path | str) -> None`: sends `textDocument/didClose`.
       - Language queries:
         - `get_definition(file_path: Path | str, line: int, character: int) -> list[dict]`: sends `textDocument/definition`.
         - `get_references(file_path: Path | str, line: int, character: int, include_declaration: bool = True) -> list[dict]`: sends `textDocument/references`.
         - `get_hover(file_path: Path | str, line: int, character: int) -> dict | None`: sends `textDocument/hover`.
       - Diagnostic storage:
         - Listens to `textDocument/publishDiagnostics` notifications.
         - Parses each diagnostic into a structured `LSPDiagnostic` dataclass (`file_path`, `line`, `character`, `end_line`, `end_character`, `severity`, `severity_name`, `message`, `source`, `code`).
         - Normalizes severity codes: 1=ERROR, 2=WARNING, 3=INFO, 4=HINT.
         - Stores active diagnostics in an in-memory dictionary keyed by file URI/path: `dict[str, list[LSPDiagnostic]]`.

    In `src/harness_core/lsp/manager.py`:
    2. Implement `LSPManager`:
       - Manages active `LSPClient` instances for a workspace, keyed by language ID.
       - Lazy initialization: starts language server client on first file access.
       - `get_diagnostics(file_path: str | None = None, severity: str | None = None) -> list[LSPDiagnostic]`: returns filtered diagnostics across all or specific files.
       - `close_all() -> None`: gracefully shuts down all active language servers.

    In `tests/test_lsp_client.py`:
    3. Author comprehensive unit test suite:
       - Test JSON-RPC framing parser with multiple messages, split chunks, and varying `Content-Length` headers.
       - Test mock stdio language server subprocess verifying initialize handshake, `didOpen`, `didChange`, and `textDocument/publishDiagnostics` notification handling.
       - Test diagnostic store filtering by severity (`ERROR`, `WARNING`, `ALL`).
       - Test definition, references, and hover query methods.
       - Test language server registry discovery across multiple file types and mock project roots.

    AVOID: Blocking indefinitely on child server startup or teardown; enforce timeouts on all requests and process terminations.
  </action>
