  <name>Implement atomic task claiming with SELECT ... FOR UPDATE SKIP LOCKED</name>
  <files>src/harness_core/db.py</files>
  <action>
    Add task claiming methods `claim_next_task` and `claim_next_task_async` to `LedgerStore` in `src/harness_core/db.py`:
    1. For PostgreSQL (`backend_type == "postgres"`):
       - Execute query inside an atomic transaction:
         ```sql
         SELECT task_id, priority, version
         FROM tasks
         WHERE status = 'QUEUED'
         ORDER BY priority DESC, created_at ASC
         FOR UPDATE SKIP LOCKED
         LIMIT 1
         ```
       - Upon selecting a candidate task row, atomically:
         - Transition status from `QUEUED` to `RUNNING` with `version = version + 1`.
         - Generate a new `attempt_id` and `lease_id`.
         - Increment `fencing_token` for the task (`COALESCE(MAX(fencing_token), 0) + 1`).
         - Insert rows into `leases` and `attempts`.
         - Append a `STATE_RUNNING` event into `task_events` with updated cryptographic hash chain.
         - Commit transaction and return claimed task metadata, attempt ID, and fencing token.
         - If no `QUEUED` tasks are available (or all are locked by other workers), return `None`.
    2. For SQLite (`backend_type == "sqlite"`):
       - Implement fallback using an atomic `BEGIN IMMEDIATE` transaction block under `self._lock`.
       - Select the highest-priority `QUEUED` task, verify version, update state, insert lease/attempt, append hash-chained event, and commit.
    3. Ensure supporting composite index exists: `CREATE INDEX IF NOT EXISTS idx_tasks_queue ON tasks (status, priority DESC, created_at ASC);`
    AVOID: Releasing locks before creating the lease record or updating task status, which would allow a race condition.
  </action>
