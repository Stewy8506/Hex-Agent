# Plan 06.02: Cross-Machine CoW Delta Archive Sync, Lease Expiry Handover & Fencing Verification

<objective>
Implement Cross-Machine Copy-on-Write (CoW) Delta Archive Sync and Safe Lease Handover with Monotonic Fencing Token Defense. When tasks run across remote worker nodes, workspace checkpoints and step outputs are exported into deterministic `.tar.gz` delta archives and registered as Content-Addressed Store (CAS) artifacts. When a worker loses connection or sleeps mid-task and its lease expires, a second worker claims the task queue with a monotonically incremented fencing token (e.g. 1 -> 2), reconstructs the workspace from the latest CoW delta archive, verifies the Merkle tree SHA, replays sealed tool calls in 0ms (< 15ms) from the call journal, and completes execution. If the stale worker wakes up and attempts to commit results or execute tool calls with the stale fencing token, the database rejects the write with `ConcurrencyFenceError` and HTTP 409 Conflict, guaranteeing zero split-brain or duplicate commits. Prove end-to-end correctness in `tests/test_cross_machine_cow_sync.py`.

Purpose: Provide robust cross-machine task mobility and failover without risking data corruption, lost work, or split-brain race conditions when distributed workers disconnect or fail.
Output: Cross-machine CoW delta archive sync engine, lease expiration takeover, fencing token defense, and `tests/test_cross_machine_cow_sync.py`.
</objective>

         - Finds all tasks where `status IN ('RUNNING', 'VERIFYING')` and the active lease has expired (`released_at IS NULL AND expires_at < now`).
         - Transitions task back to `QUEUED` with `reason_code="LEASE_EXPIRED"`, releasing the expired lease.

       - In `claim_next_task` / `claim_next_task_async`:
         - Automatically call `self.reap_expired_leases()` (or incorporate expired RUNNING tasks directly into the claim query) so abandoned tasks are immediately eligible for claim by active workers.
         - When claiming a task that previously had an expired attempt:
           - Automatically query `max_tok = SELECT COALESCE(MAX(fencing_token), 0) FROM leases WHERE task_id = ?`.
           - Assign strictly incremented `next_token = max_tok + 1` (e.g. 1 -> 2).
           - Release any prior unreleased leases for the task.
           - Insert new attempt with `fencing_token = next_token` and `worker_id = worker2`.
           - Record `LEASE_TAKEOVER` task event with payload `{"prior_fencing_token": max_tok, "new_fencing_token": next_token}`.
    2. In `src/harness_core/orchestrator.py` & `src/harness_core/gateway.py`:
       - When Worker 2 resumes execution of the claimed task:
         - Tool calls previously executed and sealed by Worker 1 are replayed in 0ms (< 15ms) via `ToolGateway` memoization from the call journal (`replayed_from_call_id`).
         - Worker 2 continues execution from the next pending step with `fencing_token = 2`.
       - Monotonic Fencing Defense (Stale Worker 1 Rejection):
         - If Worker 1 wakes up after disconnect/sleep and tries to call:
           - `begin_tool_call(..., fencing_token=1)` -> raises `ConcurrencyFenceError` (`fencing token 1 < active token 2`).
           - `seal_tool_call(..., fencing_token=1)` -> raises `ConcurrencyFenceError`.
           - `transition_task(..., fencing_token=1)` -> raises `ConcurrencyFenceError`.
         - Over HTTP REST API, this is mapped to HTTP 409 Conflict.
         - Worker 1's commit attempt is completely rejected, preventing split-brain or duplicate writes.
