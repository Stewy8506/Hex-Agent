# HEX user-experience audit

Audit date: 12 November 2026

Scope: current `main` worktree, with special attention to the recent model-discovery,
onboarding, TUI, and per-project numbering changes. This is an implementation audit,
not a visual-design review. A finding is included when the application can show a user
one state while using another state, discard a deliberate choice, or fail without a
clear recovery path.

## Executive finding

The dominant UX risk is **split configuration state**. The selected model, active
provider, profile, project, workspace, and compressor setting each have more than one
source of truth. The UI often changes the display-facing field without changing the
provider or durable configuration that execution will use. Recent fixes improve
discovery, but they do not yet make selection, execution, and persistence a single
transaction.

## Priority checklist

| Priority | User-visible flaw | Evidence | What the user experiences | Completion check |
|---|---|---|---|---|
| P0 | Direct model selection can run the old model | `src/harness_core/tui.py:1372-1380` | `/model gemini-3-flash` reports success, but changes `router.cloud_model_id` only. It does **not** update `router.cloud_provider.model_id`, which is what `generate()` uses. Interactive selection does update both at `1417-1422`. This is a confirmed “I selected X; HEX used Y” defect. | One `set_model()` operation updates router, provider, in-memory profile, and durable project configuration together; show the provider’s final model ID after switching. |
| P0 | A model switch is not durable | `src/harness_core/tui.py:1372-1380`, `1414-1424`; `src/harness_core/onboard.py:711-756` | Both `/model <id>` and interactive `/model` update memory only. Restarting the console restores the model from environment/configuration. The success wording implies the selection is saved. | State the scope in the success message and provide a default durable switch; on restart, `/model` shows the selected model. |
| P0 | Project switching does not switch the running orchestrator context | `src/harness_core/tui.py:1938-1953`; `src/harness_core/orchestrator.py:69-103` | `/project switch` changes the TUI workspace, project ID, Graphify root, and possibly only the displayed `data_dir`. It does not rebuild/rebind the router, gateway, LSP manager, CoW provider, sandbox, proof service, or project environment. A second project can therefore inherit the first project’s credentials/model/profile and internal service roots. | Implement an atomic `orchestrator.switch_project()` that hydrates config and rebinds all workspace-scoped services before the confirmation is printed. |
| P0 | Per-project task numbering is not a reliable project identity | `src/harness_core/project_registry.py:177-228`; `src/harness_core/tui.py:1938-1939`; `src/harness_core/db.py:988-1020` | The task ledger uses the registry display name as `project_id`. Two folders with the same basename (for example, two `api` repos) can share task numbering/history. `/project use api` also selects the first matching name. | Use a stable, path-derived project UUID as the ledger ID; retain name only as a label and require disambiguation for duplicate names. |
| P1 | Task sequence is unstable at equal timestamps | `src/harness_core/db.py:999-1000`, `1016-1017` | Sequence is computed with `created_at <= current.created_at`, not an ordered task key. Tasks created in the same timestamp bucket can receive the same displayed number. This especially matters under concurrent workers. | Store a per-project integer sequence at insert time, protected by a DB constraint/transaction; display that immutable sequence. |
| P1 | The configured compressor mode is ignored | `src/harness_core/config_loader.py:136-138`; `src/harness_core/router.py:211-213` | Configuration loader exports `HEX_COMPRESSOR_MODE`; router reads only `HARNESS_COMPRESSOR_MODE`. A user who configures `compressor_mode: cloud` sees a valid config but starts with local compression unless an argument is passed. | Resolve both accepted prefixes (with documented precedence) and show the source of the active mode in `/model` or `/compressor`. |
| P1 | Provider intent can be silently overridden by Antigravity discovery | `src/harness_core/router.py:183-206` | When the configured provider has no raw API key but an Antigravity OAuth session is available, the router chooses Antigravity even if configuration named another provider. The provider label in the configuration is no longer a promise. | Treat an explicit provider as authoritative. Offer a visible, opt-in fallback only after the requested provider is unavailable. |
| P1 | Config parsing differs by entry path and can silently skip project settings | `src/harness_core/config_loader.py:49-82`; `src/harness_core/router.py:82-104`, `159-171` | The loader has a no-PyYAML parser and supports `model`/`models`; router directly imports PyYAML and swallows the failure. In an installation without PyYAML, direct router construction ignores YAML settings and silently falls back to discovery/defaults. | Route every configuration read through `parse_config_yaml()` and expose config parse/selection failures in `/doctor` and startup status. |
| P1 | Model discovery failure forces manual entry with little validation | `src/harness_core/onboard.py:392-398`, `427-433`, `462-468`, `497-503` | After a live-query failure, the wizard accepts arbitrary opaque model text, then prints “Active model selected.” The invalid value is only discovered later during a task. | Identify the selected provider and failure reason, validate the entered model before saving where possible, and label offline/manual mode explicitly. |
| P1 | “Cloud reasoner” can be initialized with an empty model ID | `src/harness_core/router.py:144-190`; `src/harness_core/providers/cloud_provider.py:349-360` | For a non-Antigravity provider with no configuration and failed discovery, the router can construct a provider with `model_id == ""`. Setup appears to have proceeded until the first request fails. | Block task submission with a precise configuration action until a provider and non-empty model are resolved. |
| P2 | Status views can contradict actual execution state | `src/harness_core/tui.py:1462-1476`, `2231-2234` | `/model` reads router fields, while the completion header prefers `self.model_profile`. After a direct switch or provider fallback, the two panels may name different models/profiles. | Render all model/provider values from one resolved execution snapshot attached to the task. |
| P2 | The activity feed hides outcome information | `src/harness_core/tui.py:2115-2129` | The recent “clean activity feed” removed status, duration, and journal-replay badges. A user now sees that a tool was called but not whether it succeeded, failed, was denied, replayed, or took significant time. | Keep the compact layout, but show a short outcome badge, duration, and expandable error/preview. |
| P2 | Task cancellation can claim success without verifying cancellation | `src/harness_core/tui.py:2146-2151` | Ctrl-C stops the spinner and prints “Task cancelled by user,” but does not call `cancel_task()` or verify the task’s terminal state. A background task may continue. | Request cancellation, wait for/print confirmed state, and say “cancellation requested” until confirmed. |
| P2 | Silent exception handling hides user-actionable degraded modes | Examples: `src/harness_core/tui.py:1900-1902`, `1944-1947`, `2206-2208`; `src/harness_core/router.py:92`, `102`, `169`, `181` | Important failures (project graph refresh, task numbering, approval lookup, config parsing, model discovery) become fallback behavior without an in-product signal. The user has no way to distinguish a healthy result from a degraded one. | Replace broad silent catches on user paths with a concise degraded-state notice, a correlation/detail code, and a recovery command. |
| P2 | Startup/test output leaks low-level hardware probe errors | `src/harness_core/onboard.py:65-79` | `sysctl` stderr is not suppressed. In restricted environments the user sees raw `Operation not permitted` lines before/among normal output, as reproduced in the focused test run. | Suppress probe stderr, preserve a structured diagnostic, and show a single friendly hardware-detection fallback note only when relevant. |
| P3 | Project task count is not maintained by TUI task submission | `src/harness_core/project_registry.py:252-261`; `src/harness_core/tui.py:2132-2145` | The project listing advertises a `TASKS` column, but prompt submission does not call `touch_active(..., increment_tasks=True)`. The number can remain zero while the project has work in its ledger. | Update task count as part of task creation, or derive it from the ledger rather than duplicating it. |

## Recommended repair order

1. Establish a `ResolvedRuntimeConfig` object containing provider, provider model,
   router model, profile, compressor mode, project UUID, configuration source, and
   persistence scope. Construct it once at startup/project switch and attach a frozen
   copy to every task.
2. Replace direct TUI field mutation with explicit operations: `switch_model`,
   `switch_provider`, `switch_project`, and `switch_compressor`. Each should validate,
   update every runtime consumer, persist when requested, and return the single
   resolved state for rendering.
3. Make project identity path/UUID based; assign an immutable sequence at task insert.
4. Add degraded-mode notices rather than silent fallbacks. A useful minimum is
   `source=config|env|live-discovery|manual`, plus `degraded_reason` in `/model`,
   `/project`, and task-completion output.
5. Restore outcome semantics to the activity feed and make cancellation stateful.

## Tests that are currently missing

- Direct `/model <id>` must assert both `router.cloud_model_id` and
  `router.cloud_provider.model_id`, then assert the generated request uses that ID.
- Switch a project with distinct `.hex/config.yaml` model/provider settings and assert
  every workspace-scoped orchestrator service is re-bound before submission.
- Register two same-named folders and prove their task sequence, search scope, and
  `/project use` selection stay distinct.
- Insert concurrent/same-timestamp tasks and assert each has one immutable sequence.
- Start without PyYAML and assert router configuration equals loader configuration.
- Configure `compressor_mode: cloud` and assert the router chooses cloud mode.
- Simulate discovery/auth failure and assert the UI reports manual/degraded state,
  rather than an unqualified “active” selection.
- Interrupt an executing task and assert `cancel_task()` was called and its confirmed
  terminal state is rendered.

## Validation performed

Focused user-flow tests passed: 84 tests across live model discovery, project registry,
configuration selection, TUI, and OAuth/TUI resilience. Passing tests do not contradict
the findings: several tests encode the incomplete state mutation (for example, direct
model switching asserts only `router.cloud_model_id`) and do not cover persistence or
the request actually sent to the provider.

The run also reproduced unsuppressed `sysctl` permission messages in this restricted
environment. No production code was changed by this audit.
