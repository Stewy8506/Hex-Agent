## Phase 4 — Expand from real lifecycle integrations

- **4.1 B38/B43** `[DONE]` — The scheduler tick now runs under a cross-process, non-blocking advisory lock (`_tick_lock`: `fcntl.flock` on POSIX, `msvcrt.locking` on Windows) held on an open descriptor so the OS releases it on process death — a crash never leaves a stale lock. A tick that cannot acquire the lock is skipped (returns `[]`), giving non-overlap between concurrent scheduler processes/daemon invocations. Due jobs are claimed durably *before* execution: `next_run` is advanced to the next occurrence after the tick time and persisted before `submit_and_run`, so a crash mid-run cannot refire the same occurrence; each outcome is persisted immediately after its job. Catch-up is explicit and coalescing — an overdue job fires once and `next_run` jumps to the next future occurrence rather than replaying every missed interval; a missing/unparseable `next_run` is repaired during the claim instead of leaving the job perpetually due. Cron day-of-month/day-of-week now follow Vixie crontab(5) semantics (B43): when both fields are restricted (neither `*`) the day matches if EITHER matches (OR); when one is `*` the restricted field controls — applied consistently in both `matches()` and `next_run_after()`. Verification: 33 `tests/runtime/test_scheduler_and_daemon.py` tests pass natively on Windows (8 new: 4 Vixie OR/next-run regressions, concurrent-tick skip, crash-after-claim no-refire, coalescing catch-up, corrupt-next_run repair), including the existing happy-path/failure-alert/CLI run-due contracts. Red proofs against `HEAD` source confirm the old behavior fails the new regressions: old AND rejects a Friday-that-is-not-the-13th, old code leaves `next_run` unchanged after a mid-run crash (refire), and old code fires while the tick lock is held. The Windows `msvcrt` lock path is exercised natively by the concurrent-tick test. Job execution deadlines remain owned by the orchestrator's `submit_and_run`; no separate timeout wrapper was added.
- **4.2 B39** `[DONE]` — The background daemon descriptors now match the one-shot `schedule run-due` interval job instead of a keep-alive/restart loop. launchd: `DaemonConfig.keep_alive` defaults to `False`, so the plist omits `KeepAlive` and `StartInterval` alone drives the cadence (`KeepAlive=true` remains an explicit opt-in for persistent services). systemd: the unit is `Type=oneshot` with `Restart=always`/`RestartSec` removed, and a new `generate_systemd_timer()` emits a `.timer` (`Unit=…service`, `OnBootSec`/`OnUnitActiveSec=interval`, `Persistent=true`, `WantedBy=timers.target`); `install_systemd` writes and returns both the `.service` and `.timer` (dry-run previews both), and uninstall stops/disables/removes the timer alongside the service so no dangling trigger survives. Windows no longer falls through to systemd: `generate_task_scheduler_xml()` emits a Task Scheduler 1.2 descriptor with a `TimeTrigger`/`Repetition` `Interval=PT{interval}S`, `MultipleInstancesPolicy=IgnoreNew` (non-overlap, matching the 4.1 tick lock), unlimited `ExecutionTimeLimit=PT0S` (the orchestrator owns deadlines), and an `Exec` action that forwards the data dir via the global `--data-dir` CLI argument (Task Scheduler cannot set env vars); all text nodes are XML-escaped. `install_windows_task` registers it via `schtasks /Create /XML /F` (dry-run safe), `_get_windows_task_status` queries `schtasks /Query` (Enabled/Ready/Running = active, Disabled = inactive), and `_uninstall_windows_task` deletes via `schtasks /Delete /F` and removes the generated XML. `get_daemon_status`/`uninstall_daemon` are platform-aware (Windows → schtasks, Darwin → launchd, else systemd). The CLI `daemon install` auto-detects Windows → Task Scheduler and accepts an explicit `--schtasks` flag; the `hex uninstall` daemon cleanup reuses the platform-aware path.
